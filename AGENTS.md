# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

TypeScript project template with strict tooling: ESLint (strict type-checked, plus `unicorn` recommended), dprint formatting, commitlint, cspell, markdownlint. All scripts run via `jiti` from TypeScript.

- **`tsconfig.json` compiles on `lib: ["ES2024"]`, which is HIGHER than the ES2022 floor the sibling configs (`obsidian-dev-utils`, `obsidian-test-mocks`, `obsidian-typings-crawler`) carry.** A large block of their `unicorn` disables exists only because of that floor — `no-array-sort`, `prefer-iterator-helpers`, `prefer-promise-with-resolvers`, `prefer-set-methods` and the rest. None of those reasons hold here, so do not copy the block across: `no-array-sort` is satisfiable and enabled, and the one site that fires uses `toSorted`.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/`:
  - `eslint.config.mts` -> `scripts/eslint-config.ts`
  - `commitlint.config.ts` -> `scripts/commitlint-config.ts`
  - `.markdownlint-cli2.mjs` -> `scripts/markdownlint-cli2-config.ts`
  - `.nano-staged.mjs` -> `scripts/nano-staged-config.ts`
  - `vitest.config.ts` -> `scripts/vitest-config.ts`
- **`scripts/`** — all npm script entry points (`jiti scripts/<name>.ts`)
- **`scripts/helpers/`** — shared utilities (check-project-types, env-toggle, eslint, exec, format, git-content, markdownlint, package-manager, root, type-guards)
- **Those helpers are PEER COPIES, shared byte-for-byte with `obsidian-test-mocks` and `obsidian-typings-crawler`** — ten of the eleven files there hash identically in all three checkouts (measured 2026-09-20), and most of them descend from `obsidian-dev-utils/src/script-utils/`. A change to one is a change to all three, so sync it across rather than hand-editing a single copy. Three things to know before moving bytes in either direction:
  1. **Interface members are `readonly` function PROPERTIES here, never method shorthand.** `@typescript-eslint/method-signature-style` is `'error'` in `scripts/eslint-config.ts` — its own `property` default — as it is in `obsidian-dev-utils`, `obsidian-test-mocks`, `obsidian-typings-crawler` and `obsidian-integration-testing`, the last of which converted 29 members to reach it in a `refactor(types)!` commit. Until 2026-09-20 this repo configured the rule nowhere, and `check-project-types.ts`'s two `shouldKeep*` members sat in the method form and drifted back on every sync. The rule is in **no preset**, so deleting the line turns it off and re-opens that drift silently.
  2. **Four files differ today, and on all four the sync runs OUT of this repo rather than into it — do NOT "converge" any of them toward a sibling.** They are the four entries in `check:helpers-sync`'s `DIVERGENCE_EXCEPTIONS`, each carrying its own reasoning:
     - `git-content.ts` — the difference is entirely prose. All three copies carry identical code; the `@file` header and the `isMissingPath` comment are worded three different ways, and this repo's is the current one on what happens outside a repository (it is thrown, not reported as an absent blob).
     - `git-content.test.ts` — taken from `obsidian-test-mocks` on 2026-09-23, which carried the only copy of the suite while this repo carried the authoritative copy of the file under test. Two of the peer's five fixtures are its own repo's: its manifest name, and a vendored Inter TTF for the binary case. **Nothing here can stand in for that TTF — none of this repo's tracked files contains a NUL byte** — so that one case is the only one that builds a scratch repo, against the peer's own rule of asserting over the repository's real index, and it says why in the file. A sixth case is added, pinning the distinction the entry above is entirely about: a folder that is not a repository is thrown, not reported as an absent blob. All six are falsified against mutants of `git-content.ts` — a UTF-8 round trip, a stripped trailing newline, and `isMissingPath` pinned true and false — each caught by exactly the one case that names it.
     - `eslint.ts` — this repo has taken the exit classification that tells a **crashed linter apart from a red codebase**, and the peers have not yet. Handing the exit code to `execFromRoot` and letting it throw reports a rule that threw, a broken config and a Windows access violation exactly the way it reports real findings, so the reader goes hunting for a defect in source that was never judged. `classifyEslintExit` / `describeFailureToLint` are pinned by `eslint.test.ts`, whose stderr fixtures are transcribed verbatim from real runs — the `Oops! Something went wrong!` banner is **not** a crash marker (ESLint prints it for a mistyped path too), which is why the rule crash is separated out by the `Rule: "…"` line instead. **The same file also spends `--max-warnings 0`**, which is what makes the classifier's `clean` mean *nothing at all*: ESLint exits `0` for a run that reported WARNINGS and no errors, so without the flag a standing warning is printed, the command returns success, and CI, the hook and every sweep read the tree as clean — which is how four standing warnings across the fleet each came to need a person rather than a gate to notice them. It is spent as a **static** command part so every batch of a split command line carries it, on the `--fix` runs too, and with **no option to raise it**: a ceiling a repo can raise is a gate somebody turns off. Landing it anywhere else means measuring that repo at zero warnings first — it goes red the same day otherwise. The fleet's own `npm run lint` does **not** come from this file but from `obsidian-dev-utils`' `src/script-utils/linters/eslint.ts`, which still has neither half.
     - `exec.ts` — four fixes the peers have yet to take. `executeBatches` returned a hard-coded `exitCode: 0` with an empty `stderr` to any caller asking for details, whatever its batches did; `getMaxCommandLength` budgeted cmd.exe's whole 8191 for the inner command and so overshot by the `<ComSpec> /d /s /c ""` wrapper `spawn` adds, which made **every** full-sized batch die with *"The command line is too long."*; the aggregate's streams now drop the silent batches instead of joining them into blank lines; and the budget is now spent on the length cmd.exe will **measure** rather than the length the string holds, since `commandEscapeCommandLine` inserts a `^` per cmd meta character after the fact, so a meta-heavy batch that fitted at 8152 reached cmd at 8192 and died with the same message. Pinned by `exec.test.ts`, which drives the real batched path over a temp `node` script.
     Each of those entries **expires by construction**: once a peer converges, the gate fails on the exception that still claims a divergence, and deleting it is the signal that the port landed.
  3. **`npm run check:helpers-sync` is what gates the roster** — before it existed nothing did, and five of the eleven files had fallen behind unobserved. `check:vendored-eslint-rules` walks for the names `obsidian-dev-utils` publishes under `src/script-utils/linters/eslint-rules/`, so it can never see these files, and `obsidian-test-mocks`' `check:copy-sync` covers its docs pipeline rather than these helpers.
- **What `check:helpers-sync` asserts, and the five decisions inside it:**
  1. **Byte-identity against ONE peer, `mnaoumov/obsidian-test-mocks`.** That repo carries the richest roster (19 files against this repo's 15, re-counted 2026-09-23) and was byte-identical here on every shared file but `git-content.ts`, so it is the natural side to fetch. `obsidian-typings/obsidian-typings-crawler` carries the same helpers and is a second opinion, not a second gate: fetching both doubles the network cost to answer the same question twice. Identity can be asserted here — unlike in `check:copy-sync`, whose areas diverge semantically and which therefore records only a diff *shape*.
  2. **The roster is the TREE `scripts/helpers/`, minus `eslint-rules/`** — one predicate decides membership on both sides, so the two rosters cannot be scoped differently by accident. `@types/` is deliberately in; `eslint-rules/` is out because `check:vendored-eslint-rules` already owns it against a different upstream and a different set of deltas.
  3. **A file only one side carries is NOT drift.** The peer's roster is a superset by construction, so only the intersection is compared and anything one-sided is printed as information on a pass. Taking a peer-only helper is a decision somebody makes, not a sync a gate can demand.
  4. **A deliberate divergence is recorded in `DIVERGENCE_EXCEPTIONS` with its reason, and the record EXPIRES.** A file that differs with no entry fails; a file that has become byte-identical while an entry still claims a divergence fails too, because a stale exception is where the next real one hides. A difference that is *mechanical* goes in `TRANSFORM_ARMS` instead, which reproduces this repo's copy from the peer's. That list ships **empty** — nothing mechanical diverges today, and it is there because it is the shape the downstream repos adopt.
  5. **It reads this repo's side out of the git index**, like its sibling and for the same nano-staged reason, falling back to disk for an untracked helper. It runs from the `**/helpers/**/*.ts` nano-staged group — two globstars on purpose, since the single-star form does not reach `@types/` — and from CI, which is what catches the peer moving underneath a file nobody is editing. `CHECK_HELPERS_SYNC=0` turns it off for a run.
- **`scripts/helpers/eslint-rules/`** — custom ESLint rules under the `obsidian-dev-utils` plugin namespace, each with a `*.test.ts`: `no-async-callback-to-unsafe-return`, `no-unused-params-members`, `no-used-underscore-variables`, `params-options-name-match`, `readonly-params-options-result-members`, `require-method-template`
- **Those rule sources are VENDORED COPIES of `obsidian-dev-utils/src/script-utils/linters/eslint-rules/`, not local code — take an upstream change whole rather than hand-editing one.** The `*.test.ts` files and `rule-tester-helper.ts` are byte-identical to upstream; the sources carry exactly two standing deltas, and anything else is drift to reconcile:
  1. `from '../../../type-guards.ts'` becomes `from '../type-guards.ts'` — the helper sits one level up here, not three.
  2. `require-method-template.ts` reads its named groups with the local `ensureNonNullable` instead of upstream's `getMandatoryNamedGroup`, whose module is a 238-line `reg-exp.ts` no sibling vendors. The file says so at the import.
  `require-method-template` is vendored **only** here; `obsidian-test-mocks`, `obsidian-typings-crawler` and `obsidian-integration-testing` carry the other five.
- **There used to be a third delta — the inline `// eslint-disable-next-line unicorn/…` comments stripped on the way in — and the config now keeps two rules ON specifically so it can stay gone.** While this repo installed no `eslint-plugin-unicorn`, those lines could not be taken at all: ESLint fails the **entire** run with *"Definition for rule was not found"* on an unresolvable rule reference, and a file-scoped `'unicorn/…': 'off'` override fails the same way. Installing the plugin is only half the answer, and the other half is the trap `obsidian-typings-crawler` fell into: a rule that RESOLVES but is switched off over the file makes the directive **unused**, which `lint:fix` then deletes — the same drift by another route. So `getUnicornConfigs()`'s `scripts/helpers/eslint-rules/**` block turns off only `no-break-in-nested-loop` and `no-unreadable-for-of-expression`, and deliberately leaves `no-useless-recursion` and `name-replacements` on, because those two are what upstream's three directives name. `name-replacements` also needs `checkProperties: true` for the same reason: two of the three directives sit on an object property, which the rule's default never reaches. **Turning any of that off re-opens the delta** — `npm run check:vendored-eslint-rules` is what says so.
- **`npm run check:vendored-eslint-rules` is what enforces the paragraph above** — it lists upstream's directory, fetches each source from `raw.githubusercontent.com`, applies the three deltas as *transform arms*, and asserts byte-identity. Three things about it are load-bearing:
  1. **A delta is recorded as the transform that reproduces it, not as prose.** Accepting a new divergence means adding an arm, which every later run then enforces. Arm 3 matches upstream's `getMandatoryNamedGroup` lines as literal text, so an upstream rewrite of them no-ops the replacement and the file is reported — which is the right answer, because a moved shape wants a human's eyes.
  2. **It walks for the NAME, not the directory**, so a second vendored tree anywhere in the repo cannot hide from it. A walk that finds nothing at all is reported as a failure rather than passed.
  3. **It reads this repo's side out of the git index** (`scripts/helpers/git-content.ts`), not off disk. It runs from nano-staged beside `lint:fix` and `format`, which rewrite staged files in place; nano-staged runs its per-pattern groups with `Promise.all`, so no key order makes this follow them. Reading the index makes the race irrelevant instead of trying to lose it. An untracked copy has no staged bytes and falls back to disk.
  It also runs in CI, which the hook cannot substitute for: a copy is only staged when somebody is editing it, so upstream moving underneath a tree nobody touches is invisible to a pre-commit gate. `CHECK_VENDORED_ESLINT_RULES=0` turns it off for a run, offline or wherever the fetch is unwelcome.
- **Testing** — vitest, three projects, and which one collects a file is decided entirely by where the file lives:
  - `unit-tests` — `src/**/*.test.ts`, with `scripts/**` excluded outright. Empty in the template, which is why the root config sets `passWithNoTests`.
  - `eslint-rules` — `scripts/helpers/eslint-rules/*.test.ts`. Non-isolated and single-worker, because the rule tester keeps module-level state; `tsconfig.eslint-test.json` types the one type-aware rule.
  - `unit-tests:scripts` — the rest of `scripts/**/*.test.ts`, Node environment, default worker settings. Same name and shape as the project `obsidian-test-mocks` and `obsidian-typings-crawler` run their own copies of these files under.
- **Adding a fourth project: leave `maxWorkers` alone, or give it its own `sequence.groupOrder`.** Vitest groups specs by `groupOrder` and refuses a group holding two projects with different worker counts — *"Projects ... have different 'maxWorkers' but same 'sequence.groupOrder'"* — and the whole run then collects **nothing**, as one unhandled error rather than a failing test. That is why `eslint-rules` carries `sequence: { groupOrder: 1 }`. Measured on vitest 4.1.10; it is not a Vitest 5 concern to defer. It stayed hidden here for as long as it did only because `src/` is empty, so `unit-tests` contributed no specs and `eslint-rules` was alone in its group.
- **A test file under `scripts/` that no project's `include` covers runs NOWHERE, and `npm test` stays green.** `npm test` is a bare `vitest run`, so it reports on the projects that exist rather than on the files on disk. Before trusting a new suite, check that the test count actually moved.
- **CI** — `.github/workflows/ci.yml` runs the full gate (compile, lint, format, spellcheck, markdown lint, vendored-rules check, helpers-sync check, test) on push and PR
- **`src/`** — project source code (empty in template)
